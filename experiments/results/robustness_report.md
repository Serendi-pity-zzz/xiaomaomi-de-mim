## 3. 结论

- 对照行（强度 0）扫码与恢复全部通过，说明载体、嵌入与提取流程本身没有问题。
- 凡是会改写像素的干扰（JPEG、高斯噪声、椒盐噪声、旋转、裁剪），强度只要大于 0，秘密恢复合计只有 0/75：LSB 把信息放在最低位，重编码、插值、叠加噪声都会直接改写这些位。
- 二维码的耐受上限：高斯噪声到强度 100、JPEG 压缩到强度 100（质量约 5）、旋转到强度 20、四周裁剪到强度 20，扫码仍全部成功；同一批图在这些强度下秘密恢复全为 0——纠错码（等级 H）与 LSB 的耐受力差距就体现在这里。
- 椒盐噪声最不友好：强度刚过 20 二维码就解不出来了（椒盐把约 6% 的像素直接打成纯黑或纯白，定位图案也随之失效）。
- 遮挡是唯一「面积大反而没伤到秘密」的干扰：中心遮挡累积 13/15 仍能恢复，因为白块落在图像中部、没有压到 CAT1 条带；改成定点遮挡（压在条带上）后立刻降到 0/15。结论是遮挡的**位置**比**面积**更决定后果，也说明前端现有的中心遮挡用例不足以评估隐写鲁棒性。
- 完整性通过数与秘密恢复数在所有条件下完全相同：当前完整性判据就是 CAT1 的 HMAC，只有包头能解析时才生效。数据一旦被破坏，结果多为 unknown（无法判断）而不是 failed（判为篡改）——这正是 D 的区域认证需要补上的缺口。
- 共 86 条记录提取状态为 unknown（读不到 CAT1 标记），按约定不计为通过，也不据此断言被篡改。

## 4. 局限

- 解码器是 OpenCV，不是真实手机：手机相机 + 微信/支付宝扫码通常比 OpenCV 宽容，因此本表的扫码成功率是**保守下界**，不是手机实测值。真实扫码需按 README 演示顺序另行记录。
- Python 侧噪声用 `numpy.random.default_rng(seed)`，与浏览器 LCG 的不同实现会得到不同噪声像素，统计口径一致但不能逐像素对比。
- 完整性判据目前只是 CAT1 的 HMAC（只覆盖消息，不覆盖整幅图像），D 的分块认证接入后需重跑本实验并区分「覆盖范围内/外」。
- 载体为 `core.service.generate` 的内置猫咪并置基线，不是 A 的艺术融合成果；A 交付后传入 `--carrier` 重跑，结论才算对最终载体成立。
- 扫码后端缺失时扫码列留空；提取状态 unknown 记在 integrity_status 列，不计为通过，也不推断为篡改；裁剪后尺寸变化，PSNR 不适用，记为留空。
